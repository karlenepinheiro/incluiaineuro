1Escopo

O que foi analisado: a Edge Function ai-gateway (Supabase/Deno) por inteiro — roteamento de provider, integração Gemini, integração Vertex AI Imagen, código OpenAI existente no repositório (e por que está órfão), todos os pontos de chamada de callAIGateway() no frontend, variáveis de ambiente/secrets envolvidos (por nome, nunca por valor), e todas as regras .md de governança do projeto (docs/DO_NOT_TOUCH.md, REGRAS_SEGURANCA_INCLUIAI_2_0.md, docs/ARCHITECTURE.md, docs/SUPABASE_RULES.md, docs/CLAUDE.md, supabase/architecture.md, entre outras).

O que foi executado nesta sessão (Etapa 3): criação de dois arquivos novos dentro de supabase/functions/ai-gateway/ — _types.ts (contratos AIProvider) e _router.ts (estrutura inicial de seleção de provider) — nenhum dos dois importado por index.ts. Nenhuma outra alteração de código foi feita.

Autorização prévia da CEO (registrada nesta sessão): secret OPENAI_API_KEY será criado no ambiente Supabase (independente de eventual OPENAI_API_KEY já existente na Vercel); proibido criar VITE_OPENAI_API_KEY; proibida qualquer migration ou coluna nova (provider incluso) nesta fase — observabilidade deve reaproveitar o campo model (texto livre) já existente em ai_requests; frontend, regras pedagógicas, IncluiLAB, Biblioteca, autosave, renderer, créditos e contexto de aluno permanecem fora de escopo.

2Resumo executivo

  1. Hoje o roteamento é 100% hardcoded em Gemini/Vertex. Dentro de index.ts, o bloco aiCall() decide a função a chamar só pelo campo task (image → Vertex Imagen; json/document → Gemini JSON; text → Gemini texto). Não existe nenhuma variável de decisão de provider.
  2. Existe código OpenAI real no repositório, mas ele roda em outro runtime (Vercel) e está órfão. api/openai-generate-activity-image.ts + src/services/openaiActivityImageService.ts implementam gpt-image-1 → dall-e-3, mas nenhuma view do app importa o cliente frontend. Isso explica a evidência externa de consumo zerado na OpenAI.
  3. Rótulos de UI mentem sobre o provider real. "A4 Visual", "Premium Ilustrada" e variantes de "Adaptar" dizem (OpenAI) na descrição e usam uma função chamada buildOpenAIActivityImagePrompt, mas a chamada real é callAIGateway({task:'image'}), que sempre cai em Vertex Imagen (Google). Fora de escopo corrigir isso neste Sprint — é decisão de produto, não de infraestrutura.
  4. A tabela ai_usage_logs com coluna provider citada em supabase/architecture.md ainda não existe em produção — é um item de roadmap (Fase 8, não implantada). A tabela real hoje é ai_requests/ai_outputs (confirmado na migration 20260407174103_remote_schema.sql), com um campo model text livre — suficiente para registrar provider+modelo sem qualquer alteração de schema.
  5. Etapa 3 entregue de forma estritamente aditiva. Dois arquivos novos (_types.ts, _router.ts), nenhum import em index.ts, comportamento de produção idêntico ao anterior — verificado por busca textual (nenhuma ocorrência de _types/_router em index.ts) e por checagem sintática dos dois arquivos novos.

4Fluxo atual do ai-gateway

Congelado nesta auditoria (Etapa 2 do Sprint) como comportamento de referência — é exatamente o que o Router deve reproduzir quando AI_ROUTER_MODE=gemini.

1. Valida JWT (jose + JWKS do projeto Supabase)
2. Resolve tenant/user via _credits.ts::getTenantContext (service_role)
3. Valida body (task, prompt não vazio, ≤32.000 chars)
4. createAuditRecord (ai_requests, status=pending) — se requestType presente
5. Se task==='document' (ou json+buildContextServer): injeta contexto canônico do aluno
6. reserveCredits (RPC atomic_reserve_credits) — só se cost>0
7. aiCall():
     task==='image'          → generateVertexImage(prompt)
     task==='json'|'document'→ generateGeminiJSON(prompt, img?)
     task==='text' (default) → generateGeminiText(prompt, img?)
   via callAIWithRetryAndTimeout(fn, retries=0, timeout=90s)
8. Se json/document: validateAndRepair(result)
9. commitReservedCredits (ou release se deferCommit / erro)
10. completeAuditRecord (ai_requests + ai_outputs)
11. Se task==='document': insert em `documents`
12. Retorna { result, creditsRemaining?, auditId?, documentId?, warnings?, reservationId? }

Gemini (_vertex.ts): modelo fixo gemini-2.5-flash; generateGeminiJSON tenta responseMimeType:'application/json' e, se vazio, tenta de novo em modo texto puro; timeout de 90s por chamada via fetchWithTimeout.

Vertex AI Imagen (_vertex.ts): OAuth2 manual via JWT RS256 assinado com crypto.subtle; modelos imagen-4.0-generate-001 → imagen-4.0-fast-generate-001 (só troca em erro transitório, não em 400/403).

6Divergências encontradas

  • UI vs. execução real: labels "A4 Visual", "Premium Ilustrada", "Adaptar — Visual/Premium" dizem (OpenAI); a chamada real é sempre Vertex Imagen via ai-gateway. Não corrigido — fora de escopo do Sprint Gateway (é mudança de frontend/copy, proibida nesta fase).
  • Documentação de arquitetura vs. schema real: supabase/architecture.md descreve um schema-alvo (v2.0, roadmap) que inclui ai_usage_logs.provider; o schema real ainda usa ai_requests.model (texto livre, sem coluna provider). Tratado como fato assumido nesta auditoria — não presumido.
  • Dois caminhos de geração de imagem Imagen (Google), redundantes: um via ai-gateway (Supabase, _vertex.ts) e outro via api/generate-image.ts (Vercel, SDK @google/genai), usado só para miniaturas do IncluiLAB. Ambos fora do escopo de unificação deste Sprint.

8Casos de borda considerados

  • AI_ROUTER_MODE ausente ou com valor inválido: _router.ts::getRouterConfig() cai no default seguro 'gemini' — nunca lança erro por variável ausente.
  • Registry vazio (estado atual): selectPrimaryProvider() lança erro explícito e claro se o provider do modo configurado não estiver registrado — comportamento esperado nesta etapa, já que nenhum adapter foi criado ainda; a função não é chamada por ninguém em produção.
  • task==='document' no nível do Provider: documentado em _types.ts que a normalização document→json (já existente em index.ts hoje) precisa ser preservada quando o Router for conectado — registrado como nota, não implementado ainda (evita presumir a Etapa 4).

12Conclusão

A auditoria confirmou que o roteamento de IA do IncluiAI hoje é 100% Gemini/Vertex, hardcoded por task, sem nenhuma decisão de provider — e que o código OpenAI existente está isolado num runtime diferente (Vercel) e órfão de qualquer caller ativo. A Etapa 3 do Sprint Gateway 1 criou a estrutura de tipos (AIProvider) e o esqueleto do Router de forma estritamente aditiva, sem tocar em index.ts, sem alterar banco, frontend ou regras pedagógicas. O sistema em produção continua idêntico ao estado anterior a este Sprint. O caminho de rollback desta etapa é trivial: apagar os dois arquivos novos.
