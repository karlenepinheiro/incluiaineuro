2Correção do MIME das imagens (P0 da auditoria)

Arquivo: src/services/studentDocumentImportService.ts. Nenhuma linha do Gateway, _vertex.ts, provider ou autenticação foi tocada.

Antes

reader.onload  = () => resolve((reader.result as string).split(',')[1]); // descarta "data:image/png;base64,"

Depois

reader.onload  = () => resolve(reader.result as string); // mantém o data URL completo

// e, antes de enviar, o mimetype é revalidado e reconstruído explicitamente —
// não confia cegamente no que o FileReader/navegador adivinhou:
const mimeType = resolveAcceptedImageMimeType(file);      // 'image/jpeg' | 'image/png' | 'image/webp' | null
if (!mimeType) throw new Error('Este arquivo utiliza um formato de imagem não suportado...');
const rawDataUrl = await fileToBase64(file);
imageBase64 = rebuildDataUrlWithMimeType(rawDataUrl, mimeType);

resolveAcceptedImageMimeType usa file.type como fonte primária e só recorre à extensão quando o navegador não informa um tipo — e rejeita (não adivinha) quando a extensão e o type real se contradizem (ex.: um arquivo com type: 'application/pdf' renomeado para .png). Nenhuma conversão de bytes é feita — apenas o rótulo enviado ao Gemini passa a corresponder ao formato real, exatamente como já funcionava em ChecklistUploadModal.tsx (que serviu de referência, sem ser alterado).

A validação agora acontece assim que a professora seleciona a imagem (não só na hora de processar), então um formato incompatível é rejeitado imediatamente com uma mensagem clara.

Decisão tomada, conforme instruído: a leitura visual multipágina real não foi implementada — exigiria alterar o Gateway/provider para aceitar múltiplas imagens por chamada, o que está fora do escopo autorizado desta fase. Esse texto é gerado por buildPageDisclosureMessage(totalPages, pagesAnalyzed), calculado a partir de pdf.numPages (já lido durante a própria renderização da página, sem custo adicional) — testado em studentDocumentImportService.test.ts.

Registrado para fase futura (requer autorização própria, por alterar Gateway/provider/possivelmente custo): suportar 2–3 páginas na leitura visual.

7Proteção dos créditos — vazamento de reserva corrigido

Achado da auditoria: quando o AI Gateway já reservava o crédito (modo deferCommit) e a IA respondia com sucesso, mas o frontend decidia rejeitar o resultado depois (JSON inválido, nenhum aluno identificado, confiança muito baixa), o reservationId era descartado dentro do throw new Error(...) — ninguém no frontend sabia o ID para liberar a reserva.

Correção

Nova classe DocumentImportRejection extends Error, com um campo público reservationId: string | null. Todo ponto de rejeição que acontece depois de uma chamada bem-sucedida ao Gateway agora lança esse erro carregando o reservationId da resposta:

throw new DocumentImportRejection(
  'A imagem está ilegível ou com qualidade insuficiente...',
  response.reservationId ?? null,
);

No modal, o catch de runAIProcessing agora verifica esse campo e, se presente, chama a rotina de liberação já existente e testada (releaseReservation() → CreditTransactionService.atomicReleaseReservedCredits) antes de mostrar o erro:

const leftoverReservationId = err?.reservationId ?? null;
if (leftoverReservationId) {
  pendingReservationRef.current = leftoverReservationId;
  await releaseReservation();
} else {
  pendingReservationRef.current = null; // Gateway já liberou automaticamente (erro de provider)
}

Como isso só dispara quando a chamada ao Gateway teve sucesso (o caso em que o próprio Gateway já libera automaticamente é mutuamente exclusivo — ele só libera quando o provider falha), não há risco de liberação duplicada. A função releaseReservation() já zera a referência antes de chamar a RPC, evitando também chamada dupla se o usuário fechar o modal logo em seguida.

Casos cobertos pela correção (com teste automatizado): análise falha (JSON inválido) → reserva liberada com ID preservado; nenhum aluno identificado → idem; baixa confiança na leitura visual → idem (mesmo padrão, código análogo em mapVisualDocumentToStudentPayload). Cancelamento com o app ainda aberto já era coberto (fechar modal, trocar de modo, desmontar componente) e foi preservado sem alteração.

Valores comerciais preservados: 3 créditos (PDF/Word com texto) e 5 créditos (imagem/PDF escaneado) — nenhuma constante de custo foi alterada (src/config/aiCosts.ts não foi tocado).

Limitação que depende de banco/cron — não implementada nesta fase (conforme instruído)

Se a professora fechar a aba do navegador (crash, F5 forçado) depois que a IA processou com sucesso mas antes de clicar em "Cancelar" ou confirmar, o useEffect de cleanup do React pode não executar de forma confiável, e o crédito reservado pode continuar debitado sem devolução — não existe rotina de expiração automática (cron/RPC) no banco, e criar uma está fora do escopo autorizado desta fase (não foi criada nenhuma migration, tabela ou cron). Corrigidos apenas os casos controláveis com o aplicativo aberto, como instruído.
