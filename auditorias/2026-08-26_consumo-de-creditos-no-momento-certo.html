1Causa do problema financeiro

CONFIRMADO POR CÓDIGO — a arquitetura da Fase 1 usava deferCommit: true: o Gateway reservava o crédito, chamava o provider, e devolvia um reservationId para o frontend decidir depois quando confirmar (commit) ou liberar (release). O frontend só chamava commit dentro de handleDocxSave — ou seja, só quando o aluno era salvo. Se a professora cancelasse depois de ver a revisão (a IA já tinha sido chamada e paga ao provider), o modal chamava release — devolvendo um crédito que já correspondia a uma chamada real e paga ao Gemini.

Isso permitia exatamente o abuso descrito: analisar repetidamente, ver o resultado, cancelar sempre — custo real recorrente para o IncluiAI, consumo interno zero.

4Ponto exato de reserva, commit e release

Todos os três acontecem dentro da mesma invocação da Edge Function ai-gateway, na mesma requisição HTTP que a professora dispara ao clicar "Processar com IA" — não há mais uma segunda chamada do frontend em nenhum dos três casos:

  • Reserva: reserveCredits(), logo após resolver o provider e antes de chamá-lo (comportamento já existente, inalterado).
  • Commit: logo após validateAndRepair(result) (JSON validado) — se checkResultUsability(parsedDocument, usabilityCheck) retornar {usable: true}, cai no caminho de commit imediato já existente no Gateway para chamadas sem deferCommit (o mesmo usado por todo o resto do produto) — nenhuma lógica de commit nova foi escrita, só passou a ser alcançada por este fluxo.
  • Release: se checkResultUsability retornar {usable: false}, um throw intencional (UNUSABLE_RESULT) reaproveita o mesmo bloco catch que já liberava a reserva em falha de provider — nenhuma lógica de release nova foi escrita aqui também.

Por que isso fecha a janela de falha: como as três etapas ocorrem sequencialmente dentro de uma única execução server-side da Edge Function, nenhuma queda de conexão, fechamento de aba, F5 ou callback perdido no navegador pode interromper o meio do caminho — o resultado financeiro é decidido e persistido no banco antes da resposta HTTP sequer começar a ser enviada de volta ao navegador.

Por que o Gateway precisou ser alterado (e não dava para resolver só no frontend)

Uma solução "só visual" no frontend (ex.: chamar commit assim que a resposta chegasse, antes de mostrar a revisão) ainda deixaria uma janela real: entre "provider respondeu com sucesso" e "o navegador recebe a resposta e consegue disparar uma segunda chamada de commit", uma queda de rede ou fechamento de aba deixaria a reserva permanentemente pendurada — exatamente o cenário D do pedido. Só o Gateway, rodando no servidor como parte da mesma requisição, elimina essa janela por completo.

2 (Gateway)Alteração no Gateway — mínima, aditiva, escopo autorizado

Novo campo opcional em GatewayPayload: usabilityCheck?: { arrayField, minAverageConfidence?, confidenceField? }. Quando ausente (todo o resto do produto), zero mudança de comportamento. Quando presente (só nas 2 chamadas desta feature), o Gateway checa o array indicado antes de decidir commit/release:

// Nova função pura, sem Deno/imports remotos — testada isoladamente:
export function checkResultUsability(parsedDocument, config) {
  if (!config) return { usable: true };               // resto do produto: inalterado
  const arr = parsedDocument?.[config.arrayField];
  if (!Array.isArray(arr) || arr.length === 0)
    return { usable: false, reason: 'EMPTY_RESULT' };  // "nenhum draft pôde ser produzido"
  if (config.minAverageConfidence != null && config.confidenceField) {
    const avg = /* média do campo de confiança nos itens do array */;
    if (avg < config.minAverageConfidence)
      return { usable: false, reason: 'LOW_CONFIDENCE' }; // imagem ilegível
  }
  return { usable: true };
}

Em index.ts: const usability = checkResultUsability(parsedDocument, usabilityCheck); if (!usability.usable) throw new Error('UNUSABLE_RESULT: ...'); — reaproveitando o catch e o friendlyError() já existentes. Nada mais foi tocado: roteamento Gemini/OpenAI, Gemini default, prompts, modelos, payload de imagem, geração de imagem e todos os outros requestType permanecem byte-a-byte como estavam (nenhum deles passa usabilityCheck, logo caem sempre no if (!config) return {usable:true}).

7Duplo clique e idempotência

  • Duplo clique: isProcessingRef (um useRef booleano, checado e setado sincronamente antes de qualquer await) bloqueia uma segunda chamada de runAIProcessing enquanto a primeira ainda está em andamento — mais robusto que um useState (que só atualiza no próximo render).
  • Operation ID: cada chamada de análise agora envia um operationId próprio (crypto.randomUUID()), gerado uma vez por tentativa — testado.
  • Idempotência no banco: CONFIRMADO POR CÓDIGO (leitura, não alterado) — as RPCs atomic_reserve_credits/atomic_commit_reserved_credits/atomic_release_reserved_credits (migration 20260520000002, não tocada) já checam operation_id antes de processar e retornam o resultado já registrado se a operação já existir (idempotent: true) — infraestrutura pré-existente, sólida, reaproveitada.
  • Commit repetido: as RPCs de commit/release verificam status = 'reserved' antes de agir — uma reserva já 'committed' ou 'released' rejeita uma segunda tentativa em vez de processar de novo.
  • Retry de resposta: o frontend não implementa retry automático (nenhum wrapper de retry em aiGatewayService.ts) — não há hoje um mecanismo que reenvie a mesma requisição sozinho. Se um vier a ser adicionado no futuro reaproveitando o mesmo operationId, a idempotência do banco já o protege.

5/6Mensagens implementadas

  • Antes de processar: "A análise deste documento consumirá {3 ou 5} créditos quando os dados forem disponibilizados para revisão."
  • Botão: "Processar com IA — {3 ou 5} créditos" (inalterado).
  • Ao abrir a revisão: "Análise concluída — {N} crédito(s) utilizado(s)." — discreto, no topo da tela de revisão.
  • Em falha: "Não conseguimos analisar este documento. Nenhum crédito foi consumido." (ou a mensagem específica do Gateway, quando já menciona créditos — nunca duplicada). Saldo insuficiente ganhou mensagem própria e mais clara: "Saldo de créditos insuficiente para esta análise."
  • Cancelar depois da revisão: nenhum novo alerta (a cobrança já foi informada antes do processamento, como pedido).
  • Reprocessamento: não existe hoje um botão dedicado "tentar novamente"/"reanalisar" dentro da tela de revisão — a única forma de gerar uma nova análise é "← Trocar arquivo" → tela de upload → painel de custo → "Processar com IA" de novo. Esse fluxo já exige passar pela mensagem de custo e por um clique explícito antes de qualquer nova cobrança — satisfaz a exigência de confirmação sem precisar de uma tela nova.

13Auditoria somente leitura de reservas antigas

NÃO EXECUTADA — este ambiente de trabalho não tem conexão com o banco de produção (sem sessão/credenciais Supabase). Nenhuma tentativa de conexão foi feita. Segue a consulta sugerida, 100% somente leitura, para ser rodada por quem tiver acesso (Supabase Studio ou script autorizado):

select
  id as reservation_id,
  tenant_id,
  status,
  amount,
  metadata->>'request_type' as request_type,
  metadata->>'task' as task,
  created_at,
  expires_at,
  now() - created_at as age
from public.credit_reservations
where status = 'reserved'
  and metadata->>'request_type' in ('document_import', 'document_import_visual')
order by created_at asc;

Não expõe nome/e-mail de usuário nem qualquer dado de aluno (não faz join com users/tenants, ao contrário da view v_credit_reservations). Reservas encontradas por essa consulta seriam candidatas a limpeza manual (nunca automática) — decisão e execução ficam para quem tiver acesso ao banco, com autorização própria.

11Roteiro de validação manual

  1. Anote o saldo de créditos atual.
  2. Selecione um PNG de teste e clique "Processar com IA" (deve mostrar "...consumirá 5 créditos...").
  3. Quando a revisão abrir, confira: (a) o texto "Análise concluída — 5 créditos utilizados" aparece; (b) o saldo real já caiu 5 (confira em Configurações/Créditos).
  4. Clique "Cancelar" sem salvar.
  5. Confira que o saldo continua 5 a menos (não voltou) — este é o comportamento correto agora.
  6. Repita com um DOCX completo — confira débito de 3 ao abrir a revisão (não ao salvar).
  7. Desta vez, clique "Confirmar e salvar".
  8. Confira que o saldo não caiu de novo (o aluno é salvo sem custo adicional).
  9. Tente um arquivo inválido (ex.: .heic renomeado para .png, ou um .doc antigo).
  10. Confira que nenhum débito ocorre — o saldo permanece inalterado desde antes da tentativa.
