1Escopo

Objetivo único autorizado: colocar o Gemini/Vertex atual atrás da abstração AIProvider e do Router, preservando integralmente o comportamento atual. Sem OpenAI, sem fallback, sem alteração de regra de negócio, frontend ou banco.

O que foi feito: criação de _geminiProvider.ts (adapter fino de _vertex.ts); pequeno ajuste de comentários/mensagem de erro em _router.ts (nenhuma mudança de lógica); conexão de index.ts ao Router — resolução de provider antes da reserva de créditos e reescrita do bloco aiCall para usar provider.generateText/generateJSON/generateImage em vez de chamar _vertex.ts diretamente.

Limitação honesta desta sessão: não há Deno CLI nem Docker disponíveis neste ambiente — logo, não há como rodar deno check, deno test ou supabase functions serve localmente, nem uma chave real de Gemini para testar uma chamada de fato. A Etapa 4 foi concluída no nível estático (código implementado, revisado, com diff mínimo comprovado); a validação funcional real (chamada de verdade ao Gemini/Vertex) está PENDENTE — ver Seção 8.

2Resumo executivo

  1. Delta mínimo e cirúrgico. index.ts mudou em 3 pontos: (a) troca de import direto de _vertex.ts por import do Router/Provider; (b) registry de providers montado uma vez, em escopo de módulo; (c) resolução do provider antes da reserva de créditos + reescrita do corpo de aiCall. Tudo mais no arquivo — autenticação, tenant, contexto canônico, reserva/commit/release de créditos, auditoria, persistência de documento, formato de resposta — permanece byte-a-byte idêntico (comprovado pelo diff completo na Seção 5).
  2. _vertex.ts não foi tocado. Confirmado via git diff --stat: zero linhas alteradas. O adapter _geminiProvider.ts só chama as três funções existentes e empacota o retorno.
  3. _audit.ts e _credits.ts não foram tocados. Nenhuma mudança estrutural de auditoria ou de créditos nesta etapa, conforme instruído.
  4. Configuração inválida falha cedo e sem custo. A resolução do provider acontece antes de qualquer reserveCredits; se AI_ROUTER_MODE apontar para um provider não registrado (hoje, qualquer coisa além de 'gemini' — inclusive 'openai', que ainda não tem adapter), o Gateway retorna erro 500 claro, sem reservar créditos. Configuração ausente ou desconhecida (valor não reconhecido) já cai em 'gemini' dentro de _router.ts, herdado da Etapa 3.
  5. Validação estática completa; validação funcional real pendente. tsc --noEmit --strict não aponta nenhum erro novo introduzido por esta etapa (só os erros pré-existentes de checar código Deno com compilador não-Deno, presentes também em arquivos que não toquei). Não foi possível, porém, provar em runtime real que uma chamada de texto/JSON/imagem chega ao Gemini/Imagen e retorna corretamente — ver Seção 8 para o motivo e as opções.

4GeminiProvider — como foi implementado

supabase/functions/ai-gateway/_geminiProvider.ts (arquivo novo) exporta createGeminiProvider(): AIProvider, um objeto com três métodos que chamam exatamente as funções já existentes em _vertex.ts e empacotam o retorno (hoje uma string crua) no formato estruturado exigido pela interface AIProvider definida na Etapa 3:

MétodoImplementação
generateText(input)await generateGeminiText(input.prompt, input.imageBase64) → { text, provider:'gemini', model:'gemini-2.5-flash' }
generateJSON(input)await generateGeminiJSON(input.prompt, input.imageBase64) → mesmo formato acima
generateImage(input)await generateVertexImage(input.prompt) → { base64DataUrl, provider:'gemini', model:'imagen-4.0' }

Sem try/catch dentro do adapter — qualquer erro lançado por _vertex.ts (CONFIG_GEMINI, CONFIG_VERTEX_IMAGE, "Gemini {status}: ...", "Imagen {model} {status}: ...") propaga sem modificação até o mesmo bloco catch de index.ts que já existia — friendlyError() continua reconhecendo essas strings normalmente.

Os nomes de modelo ('gemini-2.5-flash', 'imagen-4.0') foram duplicados como constantes locais em vez de exportados de _vertex.ts, de propósito — para manter _vertex.ts com zero linhas alteradas. Eles só populam o campo model do resultado estruturado (hoje não usado por ninguém — ver Seção 9) e não influenciam qual modelo é de fato chamado, isso continua 100% decidido dentro de _vertex.ts.

Decisão de design registrada: "configuração inválida" (string não reconhecida) e "provider válido mas ainda não implementado" (openai nesta etapa) são tratados de forma diferente, de propósito. O primeiro caso já era resolvido na Etapa 3 (normaliza para 'gemini', nunca deixa a variável derrubar o Gateway). O segundo caso é uma configuração explícita e válida para uma capacidade que ainda não existe — falhar alto e claro, sem custo de crédito, é mais seguro do que silenciosamente reverter para Gemini sem avisar quem configurou.

Rollback operacional (se já estivesse em produção)

Definir (ou manter ausente) AI_ROUTER_MODE=gemini como secret do projeto Supabase. Nenhuma outra ação necessária — é o próprio default do sistema. Não exige redeploy imediato de emergência: a leitura da env var acontece a cada requisição via Deno.env.get.

Rollback de código (reverter a Etapa 4 por completo)

  3. _router.ts e _types.ts podem continuar existindo sem efeito — voltam ao estado "desconectado" da Etapa 3 automaticamente, já que nada mais os importaria.
  4. _vertex.ts, _audit.ts, _credits.ts e demais arquivos auxiliares não precisam de nenhuma ação — nunca foram alterados.

Como nada foi deployado (ver Seção 1/info-bar), o rollback de código nesta fase é, na prática, apenas descartar o working tree local — nenhum ambiente real precisa ser revertido.
