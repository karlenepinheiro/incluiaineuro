1Escopo

O que foi feito: auditoria completa do frontend para localizar todo caminho que chama auth.signUp() ou equivalente (signInWithOAuth), verificação linha a linha de que a criação de conta só ocorre após confirmação positiva de compra aprovada, execução do build de produção para confirmar que nada quebrou, e levantamento de textos residuais de FREE/gratuito no código.

O que NÃO foi feito: nenhuma alteração em banco de dados, trigger, função, migration ou schema. Nenhuma conta existente foi tocada. Nenhuma correção foi aplicada ao trigger create_user_profile_on_signup() — essa é a pendência da Fase 0.

Achado principal desta auditoria: a barreira de frontend pedida já estava implementada no código atual (sprint de 02/07/2026, "Implementação — Validação de Compra antes do Cadastro", registrada em auditorias/2026-07-02_implementacao-validacao-compra-antes-do-cadastro.html). Este documento reverifica linha a linha essa implementação contra as regras detalhadas desta tarefa emergencial, confirma que ela continua correta e íntegra, roda o build, e documenta um gap residual não coberto por nenhuma auditoria anterior (Seção 6).

4Fluxo LoginScreen — verificação bloqueante

Verificado em src/components/LoginScreen.tsx, função handleSubmit (aba "Criar conta"):

setLoadingPhase('verifying');
let purchaseResult;
try {
  purchaseResult = await checkPurchaseByEmail(normalizedEmail);
} catch {
  // Erro técnico de rede/timeout — NÃO cria conta como fallback
  ...
  setPurchaseModalType('network_error');
  setShowPurchaseModal(true);
  return;
}

const isApproved =
  purchaseResult.found &&
  purchaseResult.status === 'APPROVED' &&
  purchaseResult.product_key !== 'UNKNOWN';

if (!isApproved) {
  ...
  setPurchaseModalType('not_found');
  setShowPurchaseModal(true);
  return;  // ← auth.signUp() NUNCA é chamado aqui
}

// PASSO 2: compra confirmada — só agora cria a conta
setLoadingPhase('creating');
await onRegister(formData.name, formData.email, formData.pass, formData.phone, formData.cpf);

onRegister é handleRegister em App.tsx, que chama supabase.auth.signUp() — e só é invocado depois do return acima nunca ter sido alcançado.

5Fluxo ActivationView — verificação bloqueante

Verificado em src/components/ActivationView.tsx. O formulário de cadastro (com o botão que chama handleRegister, que executa auth.signUp()) só é renderizado quando state === 'approved'. Esse estado só é setado dentro de runCheck():

const result = await checkPurchaseByEmail(emailToCheck);
if (!result.found)                       { setState('not_found');       return; }
if (result.status === 'PENDING')         { setState('pending');         return; }
if (result.product_key === 'UNKNOWN')    { setState('unknown_product'); return; }
...
setState('approved');  // ← só aqui o formulário de cadastro aparece

Não há caminho de código entre idle/checking e o formulário de signUp() que não passe por uma compra APPROVED com produto reconhecido.

6Google OAuth — caminho não bloqueado, porém inacessível na UI

handleGoogleLogin() em App.tsx chama supabase.auth.signInWithOAuth({ provider: 'google', ... }) sem qualquer verificação de compra. Isso é funcionalmente equivalente a auth.signUp() do ponto de vista do trigger de banco: um usuário Google novo também dispara on_auth_user_created e recebe FREE automaticamente.

Por que isso não é corrigido nesta ação emergencial:

  • O botão de login com Google não é renderizado em nenhuma tela hoje — LoginScreen.tsx recebe a prop onGoogleLogin mas não a usa (comentário no código: "Mantido para compatibilidade com App.tsx — não exposto na interface"). Não há vetor de UI ativo hoje.
  • Corrigir esse caminho corretamente exige verificar a compra depois do redirecionamento do Google retornar (o e-mail só é conhecido nesse momento), não antes — é uma mudança de padrão diferente da usada em LoginScreen/ActivationView, com risco real de quebrar login de clientes pagantes que já usam Google para entrar, se feita às pressas.
  • Esse mesmo risco já havia sido identificado na auditoria de 02/07/2026 e recomendado para uma fase própria ("Fase 3 — Google OAuth, médio prazo"), não para a correção emergencial.
Gap residual documentado, não corrigido: se o botão de Google for reativado no futuro sem uma guarda equivalente (verificação pós-retorno do OAuth), essa seria uma nova porta para contas FREE automáticas. Recomenda-se tratar isso formalmente antes de qualquer reativação do login Google — ver REGRAS_SEGURANCA_INCLUIAI_2_0.md seção 9 (proibido "criar FREE automaticamente").

10O que esta barreira NÃO resolve

Declaração explícita: esta é uma barreira emergencial de frontend. Ela impede que a aplicação web do IncluiAI crie contas FREE sem compra aprovada. Ela não corrige, não desativa e não altera o trigger create_user_profile_on_signup() no banco de dados Supabase.
  • Qualquer chamada direta à API do Supabase Auth (fora do frontend da aplicação — script, ferramenta externa, chamada manual) ainda dispara o trigger e cria conta FREE com 60 créditos, exatamente como documentado em auditorias/2026-07-08_achados-diagnostico-fase-0-etapas-a-d-incluiai-2.0.html.
  • O botão de login Google, se reativado sem uma guarda equivalente pós-retorno OAuth, reabre a mesma porta (Seção 6).
  • A correção definitiva — desativar ou substituir o trigger de forma segura — permanece como pendência formal da Fase 0, e deve seguir a ordem obrigatória de REGRAS_SEGURANCA_INCLUIAI_2_0.md: diagnóstico → confirmação de schema → proposta → aprovação da CEO → backup/plano de rollback → execução em ambiente seguro → produção → nova auditoria.
