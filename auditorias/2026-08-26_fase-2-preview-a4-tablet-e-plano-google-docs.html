ACausa real do crash na prévia A4 (Safari/WebKit)

CONFIRMADO POR REPRODUÇÃO REAL EM NAVEGADOR — não é uma suposição estática. A versão instalada de pdfjs-dist (5.7.284) usa, no seu próprio código, Map.prototype.getOrInsertComputed(...) — um método nativo do proposal TC39 "Map/Set Upsert", já disponível no V8/Chromium mas ainda não implementado no motor JavaScript do Safari/WebKit em uso nos iPads. Isso derruba PDFPageProxy.render() (via WorkerTransport.getOptionalContentConfig(), no thread principal) com exatamente o erro relatado.

Como foi confirmado (sem precisar de um iPad físico)

Como não há binário WebKit disponível neste ambiente (só Chromium via Playwright), a causa foi reproduzida simulando a ausência do método — a mesma condição real do Safari — em um navegador de verdade:

  1. Gerado um PDF real de teste (jsPDF) e carregado com o mesmo pdfjs-dist usado em produção, em uma página servida localmente e aberta no Chromium real.
  2. Cenário base (Chromium normal, método nativo presente): renderização com sucesso.
  3. Cenário simulando Safari (delete Map.prototype.getOrInsertComputed antes de qualquer script rodar): erro reproduzido literalmente — "this[#methodPromises].getOrInsertComputed is not a function", disparado dentro de PDFPageProxy.render() → WorkerTransport.getOptionalContentConfig(). Mesmo mecanismo do erro relatado.
  4. Cenário com a correção aplicada (mesma ausência simulada + polyfill): renderização volta a funcionar.

A geração do PDF em si (jsPDF, em PDFGenerator) não usa pdfjs-dist — por isso continuou funcionando mesmo com a prévia quebrada, exatamente como relatado.

BCorreção de compatibilidade aplicada

Novo arquivo src/utils/pdfjsCompat.ts: um polyfill mínimo, sem dependências novas, que implementa a mesma semântica do método nativo quando ausente (idempotente — não faz nada quando o motor já suporta nativamente). Chamado no topo de FormalPdfPreview.tsx e EstudoCasoPdfPreview.tsx, antes de qualquer uso de pdfjs-dist.

export function ensurePdfjsMapUpsertCompat(): void {
  // Map.prototype.getOrInsertComputed e WeakMap.prototype.getOrInsertComputed —
  // só define se o motor ainda não tiver nativamente.
}

Escopo do polyfill: só o thread principal, onde o erro relatado foi reproduzido (PDFPageProxy.render() roda no thread principal). O worker interno do pdfjs-dist roda em sua própria realm JS e não é afetado por este polyfill — não injetei nada dentro do worker porque isso exigiria envolver o script do worker de um jeito que não pude verificar com segurança neste ambiente (sem WebKit real para testar). Se o mesmo erro vier a ocorrer dentro do worker, o fallback amigável (Seção C) garante que a professora nunca veja um erro técnico — isso fica registrado como limitação honesta, não como "corrigido com certeza absoluta".

Recomendação de fast-follow (não feito nesta fase, fora do escopo autorizado): o mesmo polyfill deveria ser chamado também em src/services/studentDocumentImportService.ts (Cadastro Inteligente), que usa pdfjs-dist do mesmo jeito e está igualmente exposto a este crash em iPad.

CFallback amigável — nunca mais mostra erro técnico

A tela de erro de FormalPdfPreview/EstudoCasoPdfPreview deixou de exibir {error} (que antes podia mostrar exatamente o texto técnico "getOrInsertComputed is not a function"). Agora sempre mostra:

"Tivemos dificuldade para exibir a prévia neste navegador. Seu documento está preservado e você pode abri-lo ou baixá-lo normalmente."

Com três ações: Abrir PDF (nova aba, mesmo blob já gerado), Baixar PDF (download direto do mesmo blob, via atributo download), Tentar novamente (incrementa um retryToken incluído nas dependências do efeito — refaz somente a prévia, chamando de novo PDFGenerator.generateFromSections + a renderização em canvas; não chama IA, não toca banco, não consome créditos). O erro técnico real continua sendo logado via console.error só para diagnóstico — nunca na tela.

DWord e Google Docs — duas opções obrigatoriamente separadas

Baixar Word (.docx): rótulo do botão em DocumentWorkspace.tsx atualizado para "Baixar Word (.docx)" (era "Baixar Word"). Comportamento não mudou — continua reutilizando o pipeline Word já validado (wordExportService.ts), sem login, sem tocar Google, preservando estilos/tabelas/margens/imagens/cabeçalhos/rodapés.

Abrir no Google Docs: NÃO implementado nesta fase — confirmado por busca em todo o código-fonte: não existe nenhuma infraestrutura de OAuth do Google nem de Google Drive API no projeto hoje (as únicas menções a "google" são Google Fonts). Implementar isso de forma segura e real exige peças que não existem — Client ID/Secret OAuth, um fluxo de autorização, uma Edge Function para trocar o código por token sem expor segredo no frontend, e uma tabela para guardar o token com segurança. Nada disso foi criado nesta fase, conforme instruído ("não improvise").

O que você precisará configurar no Google Cloud (checklist para autorização futura)

  1. Criar/selecionar um projeto no Google Cloud Console.
  2. Ativar a "Google Drive API" para esse projeto.
  3. Configurar a tela de consentimento OAuth: nome do app, e-mail de suporte, logo (respeitando as diretrizes de marca do Google — não usar o logotipo oficial do Google de forma incorreta), URL de Política de Privacidade e Termos de Uso (o Google exige isso mesmo para o escopo mínimo drive.file).
  4. Adicionar exatamente o escopo drive.file — evita a verificação de segurança pesada exigida para escopos sensíveis (como o escopo drive completo).
  5. Criar a credencial "OAuth 2.0 Client ID", tipo "Web application", com as origens JavaScript autorizadas e o(s) redirect URI(s) do domínio de produção do IncluiAI.
  6. Enviar o app para verificação do Google antes de sair do modo "Testing" (mesmo com drive.file, o processo de verificação de marca ainda é necessário para uso em produção com usuários reais).
  7. Depois de aprovado: o Client ID pode ir ao frontend (não é segredo); o Client Secret vai só como secret da Edge Function (Supabase), nunca no frontend.

Privacidade e segurança (já mapeadas para quando for autorizado)

  • Arquivo criado como privado por padrão (comportamento padrão do Drive — não compartilhar automaticamente).
  • Nunca colocar Client Secret no frontend — só na Edge Function.
  • Nenhuma URL com dados do aluno — só o fileId, opaco.
  • Nenhum conteúdo do documento em log — só metadados técnicos (status, latência).
  • Refresh token nunca no localStorage do navegador — só na tabela nova, com RLS, acessada apenas pela Edge Function via service role.
  • Botão desabilitado durante a chamada (evita duplo clique criando dois arquivos).
  • Tratamento explícito de popup bloqueado e sessão OAuth expirada, com mensagem clara para tentar de novo.
  • Se tecnicamente possível (token info do Google), mostrar qual conta Google está sendo usada antes de confirmar o envio.

Nenhuma dessas peças foi criada. Este é um plano para autorização própria e separada — nada aqui foi implementado.
