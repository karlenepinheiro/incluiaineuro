1Escopo

O que foi feito: leitura direta dos arquivos-fonte do repositório que definem activate_purchase_for_user, reconcile_pending_activations e da função administrativa changePlan (frontend), para levantar hipótese sobre por que tenants.plan_id ficou desatualizado nos 9 casos encontrados pela CEO. Também foram preparadas queries somente leitura para confirmar essas definições contra o banco ao vivo.

O que NÃO foi feito: nenhuma query foi executada no Supabase nesta etapa (isso cabe à CEO rodar). Nenhuma correção foi proposta como SQL. Nenhum dado foi alterado.

Natureza da evidência: a análise abaixo é baseada no arquivo de migration mais recente encontrado no repositório para essas funções (supabase/migrations/20260618000001_fix_subscription_period_anchoring.sql, v7). Isso é uma hipótese fundamentada em código-fonte, não uma confirmação contra o banco ao vivo — o próprio histórico deste projeto já mostrou casos de arquivo local divergente de produção. A Seção 4 fornece as queries para fechar essa confirmação.

2Resumo executivo

  1. Confirmado por leitura de código: nem activate_purchase_for_user nem reconcile_pending_activations (versão v7/v2, 18/06/2026) atualizam tenants.plan_id. Ambas atualizam subscriptions.plan_id, profiles.plan, credits_wallet, credits_ledger e kiwify_purchases.activated_at — mas nunca tocam a tabela tenants. Isso bate exatamente com o padrão que a CEO encontrou nos 9 clientes.
  2. Existe uma função administrativa (billingService.ts → changePlan) que já atualiza as 4 tabelas corretamente, inclusive com comentário explícito no código: "Altera o plano de uma assinatura (admin) — atualiza subscriptions + tenants + profiles + credits_wallet". Isso mostra que o padrão correto já é conhecido e implementado em um caminho manual — só não foi replicado no caminho automático da Kiwify.
  3. O impacto real no app do cliente parece ser baixo, porque as duas funções que resolvem o plano efetivo do usuário no frontend (databaseService.ts e subscriptionService.ts) usam subscription.plan_id como fonte primária, com tenant.plan_id apenas como fallback — e nos 9 casos a subscription já está correta. Ou seja, é provável que esses 9 clientes já estejam usando o app com o plano certo.
  4. Mas o Dashboard da CEO tem um caminho que lê tenant.plan_id diretamente, sem fallback (ceoService.ts, laço de fallback para tenants que não aparecem na view v_ceo_subscribers) — esse é o caminho mais provável pelo qual a CEO viu esses 9 clientes como FREE no painel administrativo.
  5. Ainda não confirmado contra o banco ao vivo — a Seção 4 traz as queries para validar isso antes de qualquer correção ser proposta como definitiva.

4.3 — Confirmar o alcance real do problema (quantos tenants, não só os 9 já achados)

Tenants com subscription PRO/MASTER ativa mas plan_id de tenant divergentePronta — usa apenas colunas já confirmadas na Fase 0
SELECT
  t.id AS tenant_id,
  t.plan_id AS tenant_plan_id,
  s.plan_id AS subscription_plan_id,
  s.status AS subscription_status
FROM public.tenants t
JOIN public.subscriptions s ON s.tenant_id = t.id
WHERE s.status = 'ACTIVE'
  AND s.plan_id IS NOT NULL
  AND t.plan_id IS DISTINCT FROM s.plan_id;
Esta última query estima quantos tenants estão no mesmo estado dos 9 já encontrados — importante para saber se é um problema pontual ou sistemático antes de propor qualquer correção em lote.

6Comparação com o padrão já usado no admin (changePlan)

A função changePlan(tenantId, newPlanCode) em src/services/billingService.ts — usada quando a CEO/admin troca o plano de um cliente manualmente pelo painel — já atualiza as 4 tabelas relevantes, com o próprio comentário do código declarando essa intenção:

/** Altera o plano de uma assinatura (admin) — atualiza subscriptions + tenants + profiles + credits_wallet */
async changePlan(tenantId: string, newPlanCode: string): Promise<void> {
  ...
  // 1. subscriptions.plan_id
  await supabase.from('subscriptions').update({ plan_id: planRow.id, status: 'ACTIVE' }).eq('tenant_id', tenantId);

  // 2. tenants.plan_id
  await supabase.from('tenants').update({ plan_id: planRow.id }).eq('id', tenantId);

  // 3. profiles.plan — garante que o usuário veja o plano correto imediatamente após reload
  await supabase.from('profiles').update({ plan: planCode }).eq('tenant_id', tenantId);

  // 4. credits_wallet — reseta balance para o limite do novo plano
  ...
}
Conclusão desta seção: o padrão "atualizar as 4 tabelas juntas" já é conhecido e implementado no caminho manual. O caminho automático da Kiwify (activate_purchase_for_user/reconcile_pending_activations) ficou incompleto em relação a esse mesmo padrão — muito provavelmente um esquecimento ao evoluir a função em versões anteriores (v6→v7), não uma decisão deliberada.

7Avaliação de impacto real no usuário

  • App do cliente (o que o professor/AEE usa no dia a dia): resolve o plano via subscriptionService.getActiveSubscription() e via databaseService.ts, ambos usando subscription.plan_id como fonte primária. Como nos 9 casos a subscription está correta, é provável que esses clientes já estejam vendo e usando o plano certo no app — a inconsistência parece estar "silenciosa" do ponto de vista do cliente final.
  • Painel da CEO: tem dois caminhos. O caminho principal usa a view v_ceo_subscribers (que, conforme o diagnóstico de 16/06/2026, já resolve plano com COALESCE(subscription.plan_id, tenant.plan_id) — também prioriza subscription). Mas existe um caminho de fallback em ceoService.ts, usado apenas para tenants que não aparecem na view principal, que lê tenant.plan_id diretamente, sem nenhum fallback para subscription. Se os 9 tenants caírem nesse segundo caminho (por não aparecerem em v_ceo_subscribers por qualquer motivo), o painel mostraria FREE para eles — o que bate com o que a CEO observou.
  • Ainda não confirmado: se os 9 tenants realmente caem no caminho de fallback do ceoService.ts, ou se há algum outro ponto do sistema (Edge Function, RLS, relatório) que leia tenants.plan_id diretamente sem fallback. As queries da Seção 4.2 (busca por funções que mencionam tenants+plan_id) ajudam a fechar isso no lado do banco; no frontend, os arquivos já mapeados na Seção 3 cobrem os principais candidatos.

8Novo gap encontrado — profiles pode ter tenant_id

A função changePlan() executa supabase.from('profiles').update({ plan: planCode }).eq('tenant_id', tenantId) — isso é evidência de código-fonte de que a tabela profiles possui uma coluna tenant_id, o que contradiz a suposição anterior (relatório de achados A-D, 08/07/2026) de que o único vínculo entre profiles e tenants seria indireto, via e-mail passando por users.

9Proposta conceitual de correção (não executar ainda)

Esta seção é só uma proposta para aprovação futura da CEO — nenhum SQL de alteração foi gerado, e nada deve ser executado a partir daqui sem passar pelas etapas 5-9 da ordem obrigatória em REGRAS_SEGURANCA_INCLUIAI_2_0.md (aprovação → backup/rollback → execução segura → produção → registro).

Correção estrutural (a função em si)

  • Estender activate_purchase_for_user e reconcile_pending_activations para também atualizar tenants.plan_id no mesmo bloco em que subscriptions.plan_id é atualizado — replicando exatamente o padrão já usado em billingService.changePlan().
  • Deve ser a mesma transação (mesma função plpgsql), não uma chamada separada — para evitar reintroduzir o mesmo tipo de inconsistência parcial.

Correção de dados (backfill dos 9 casos já encontrados, e quaisquer outros que a query 4.3 revelar)

  • Corrigir tenants.plan_id individualmente para cada tenant afetado, usando o subscriptions.plan_id ativo como fonte de verdade (não em lote automático sem revisão, conforme regra de segurança).
  • Registrar a origem da correção (ex: coluna/log de auditoria, se existir, ou ao menos um registro manual em auditorias/) para cada tenant corrigido.

O que esta proposta NÃO inclui

  • Nenhum UPDATE/ALTER real nesta etapa.
  • Nenhuma decisão sobre remover o uso de tenants.plan_id em vez de corrigi-lo — essa é uma alternativa possível (já que o app não parece depender dele diretamente) a ser discutida com a CEO: corrigir o dado vs. parar de manter esse dado se ele for redundante. Ambas as opções devem ser avaliadas antes de decidir.

10Riscos

  • Risco atual, moderado: qualquer código futuro (ou já existente e não mapeado) que leia tenants.plan_id como fonte única, sem fallback, herda esse bug silenciosamente para qualquer um dos tenants afetados.
  • Risco caso a subscription seja removida/recriada: se a linha de subscriptions de um desses tenants for apagada ou o plan_id zerado por qualquer motivo futuro, o fallback subscription.plan_id ?? tenant.plan_id passaria a devolver o valor stale de tenants.plan_id (FREE) — nesse momento o bug se tornaria visível para o cliente final.
  • Risco de escopo desconhecido: os "9 clientes" são os que a CEO já encontrou manualmente — a query 4.3 é necessária para saber se são exatamente 9 ou se há mais casos não descobertos ainda.
