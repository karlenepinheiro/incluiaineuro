1 Escopo desta implementação
ℹ️
Arquivos alterados neste sprint: apenas src/components/LoginScreen.tsx. Nenhum arquivo de backend, trigger, migration, webhook, Edge Function, schema ou tabela foi alterado. O gate de compra é 100% frontend — chama o RPC check_purchase_by_email (já existente e com GRANT para anon).
O que foi feito
  • Remoção total do botão Google (JSX + estado googleLoading + handler handleGoogle + ícone SVG)
  • Remoção do divisor "ou" entre os botões
  • Verificação bloqueante de compra Kiwify antes de qualquer chamada a onRegister/auth.signUp()
  • Modal de compra não localizada (3 ações: WhatsApp, verificar novamente, revisar e-mail)
  • Mensagem exata aprovada pela CEO no modal
  • Feedback de progresso em duas fases: "Verificando compra..." e "Criando conta..."
  • Remoção de todos os textos "gratuita/gratuito/gratuitamente"
  • Texto do rodapé: "Já fez sua compra? Criar conta" (tab login) / "Já tem conta? Entrar" (tab cadastro)
  • Callout informativo verde quando compra é encontrada no blur do campo e-mail
  • Normalização canônica do e-mail: email.trim().toLowerCase()
  • Prop onGoogleLogin mantida na interface (opcional) para compatibilidade com App.tsx
O que NÃO foi alterado
  • src/App.tsx — handleRegister, handleGoogleLogin, props do LoginScreen
  • Triggers PostgreSQL (handle_new_user, create_user_profile_on_signup)
  • Edge Functions, webhooks Kiwify, migrations, schema
  • RPC check_purchase_by_email (usada, não alterada)
  • src/services/purchaseActivationService.ts
  • src/config/contact.ts
  • Qualquer outro componente ou serviço do projeto
2 Fluxo anterior (antes desta implementação)
1
Usuário preenche o formulário de cadastro
Nome, e-mail, telefone, CPF, senha, confirmar senha.
2
handleEmailBlur — verificação informativa (não bloqueante)
Ao sair do campo e-mail, a UI chamava checkPurchaseByEmail e mostrava um callout verde se encontrada. Mas não bloqueava o cadastro.
3
handleSubmit → onRegister → auth.signUp() — SEM verificação de compra
Qualquer e-mail, mesmo sem compra Kiwify, resultava em conta criada. Os triggers PostgreSQL provisionavam o tenant como FREE com 60 créditos.
4
Trigger handle_new_user + create_user_profile_on_signup
Qualquer auth.users INSERT criava tenant FREE automaticamente. Brecha comercial crítica.
🔴
Problema crítico: era possível criar uma conta IncluiAI sem compra, obtendo acesso FREE com 60 créditos de IA gratuitamente. O botão Google também contornava qualquer verificação.
3 Novo fluxo (após implementação)
1
Usuário preenche todos os campos do formulário
Nome, e-mail, telefone (com máscara), CPF (com máscara + validação mod11), senha e confirmar senha. Formulário único — sem etapa separada de verificação de e-mail.
2
Clica em "Criar conta" → validação dos campos
Telefone com DDD, CPF válido (algoritmo mod11), senha ≥ 6 caracteres, senhas iguais.
3
Fase 1 BLOQUEANTE: "Verificando compra..."
Chama checkPurchaseByEmail(email.trim().toLowerCase()) → RPC check_purchase_by_email.
Condição de aprovação: found=true AND status='APPROVED' AND product_key !== 'UNKNOWN'
4a
Compra NÃO aprovada → Modal de compra não localizada
auth.signUp() NÃO é chamado. Modal exibe mensagem exata aprovada + 3 ações.
Também cobre: erro de rede (network_error), compra com product_key='UNKNOWN'.
4b
Compra aprovada → Fase 2: "Criando conta..."
Apenas neste caso onRegister() é chamado, que internamente chama auth.signUp(). Os triggers PostgreSQL provisionam o tenant — mas a conta Kiwify ativará o plano correto logo após.
5
Conta criada com sucesso
Mensagem de sucesso exibida. O fluxo de ativação de plano Kiwify é responsabilidade do webhook (sprint anterior).

5 Detalhes técnicos da implementação
Verificação bloqueante — lógica central
// Após validação dos campos locais: setLoadingPhase('verifying'); let purchaseResult; try { purchaseResult = await checkPurchaseByEmail(normalizedEmail); } catch { // Erro de rede — NÃO cria conta como fallback setPurchaseModalType('network_error'); setShowPurchaseModal(true); return; // ← auth.signUp() NÃO é chamado } const isApproved = purchaseResult.found && purchaseResult.status === 'APPROVED' && purchaseResult.product_key !== 'UNKNOWN'; if (!isApproved) { setPurchaseModalType('not_found'); setShowPurchaseModal(true); return; // ← auth.signUp() NÃO é chamado } // Único caminho que chega aqui: compra aprovada e product_key válido setLoadingPhase('creating'); await onRegister(...);

9 Riscos e limitações conhecidas
⚠️
Limitação principal (backend não alterado): os triggers PostgreSQL handle_new_user e create_user_profile_on_signup ainda criam tenants FREE automaticamente para qualquer INSERT em auth.users. O gate frontend impede que usuários normais criem conta sem compra, mas um acesso direto à API Supabase auth.signUp() (ex: curl, script de automação) ainda contornaria o gate. O hardening de backend (RLS, trigger condicional) deve ser feito em sprint futuro.
RiscoClassificaçãoStatus
Acesso direto à API Supabase sem passar pelo frontend Alto Pendente — hardening backend futuro
Google OAuth ainda funciona se URL acessada diretamente Alto Botão removido da UI; provider ainda habilitado no Supabase dashboard
Conta criada antes da ativação do plano Kiwify pelo webhook Médio Janela de tempo mínima; webhook ativa em segundos
RPC check_purchase_by_email inacessível (Supabase offline) Médio Modal network_error exibido; nunca cria conta como fallback
Usuário usa e-mail diferente do informado na Kiwify Médio Modal orienta a usar o e-mail da compra + WhatsApp para suporte
product_key = 'UNKNOWN' (produto não mapeado) Médio Tratado como "não aprovado" — usuário vai para WhatsApp
