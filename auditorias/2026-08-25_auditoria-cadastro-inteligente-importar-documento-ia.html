AResumo executivo (linguagem simples)

O recurso existe e não é "fachada": há upload real, leitura real de PDF/Word, envio real para a IA (o mesmo Gateway usado no resto do produto), uma tela de revisão editável de verdade, e um controle de créditos bem desenhado (reserva → confirma/libera, nunca cobra em caso de falha de IA). Isso é bom e deve ser preservado.

Mas encontramos quatro causas concretas e verificáveis no código que explicam por que professoras relatam falha de interpretação:

  1. Fotos e imagens PNG/WEBP são enviadas ao modelo de IA com o rótulo de tipo errado (identificadas como JPEG mesmo não sendo). Isso pode fazer a IA falhar silenciosamente ou ler mal a imagem. Só arquivos .jpg/.jpeg escapam do problema por coincidência de rótulo padrão.
  2. PDF ou foto escaneada: apenas a primeira página é analisada — sempre, mesmo que o documento tenha 5 páginas. Isso é avisado na tela, mas é uma limitação estrutural séria para laudos e anamneses reais, que raramente cabem em 1 página.
  3. Documentos longos (PDF digital ou Word) são cortados em 8.000 caracteres antes de chegar à IA, e o PDF de texto só lê as 5 primeiras páginas — sem qualquer aviso à professora de que o resto do documento foi ignorado.
  4. Word antigo (.doc) não é aceito, apesar de a interface anunciar "Word" de forma genérica.

Também encontramos um risco de cobrança indevida: se a professora fechar a aba do navegador (não pelo botão "Cancelar") depois que a IA já processou o documento mas antes de confirmar o salvamento, o crédito reservado pode ficar debitado permanentemente — não localizamos nenhuma rotina automática (cron/job) que expire e devolva reservas de crédito abandonadas.

Nada disso exige trocar o Gateway, o provider ou criar tabelas novas. São correções pontuais e de baixo risco — ver Seção T/U.

FSituação real do PDF digital

CONFIRMADO POR CÓDIGO — biblioteca: pdfjs-dist, execução 100% no navegador (não no backend, não em Edge Function). Worker configurado via pdfjsLib.GlobalWorkerOptions.workerSrc apontando para o build local do worker (studentDocumentImportService.ts:25-28) — configuração correta.

  • Páginas analisadas: Math.min(pdf.numPages, 5) — documentos com mais de 5 páginas perdem conteúdo silenciosamente, sem nenhum aviso na interface (studentDocumentImportService.ts:403).
  • Truncamento por caracteres: o texto extraído (de PDF ou de DOCX) é cortado em text.substring(0, 8000) antes de entrar no prompt (studentDocumentImportService.ts:178) — para uma anamnese longa ou um laudo com múltiplas seções, isso pode cortar exatamente as informações do fim do documento (ex.: assinatura do profissional, CID, recomendações), sem aviso.
  • Ordem/concatenação: o texto de cada página é concatenado em ordem (fullText += pageText + '\n'), mas dentro de uma página os itens de texto são apenas unidos por espaço (item.str).join(' ')) — colunas ou tabelas podem embaralhar a ordem de leitura, pois pdfjs retorna itens de texto na ordem do stream do PDF, não necessariamente na ordem visual quando há colunas.
  • Fallback quando texto é ruim: existe — se o texto extraído tiver menos de 80 caracteres, o sistema já reclassifica como pdf-image e usa a rota visual (extractTextFromPdf retorna null). Mas esse limiar (80 chars) não distingue um PDF "quase todo escaneado com uma linha de cabeçalho digital" — nesse caso passaria como "PDF de texto" com conteúdo insuficiente.
  • PDF protegido por senha ou corrompido: sem mensagem específica. pdfjsLib.getDocument(...).promise lança exceção; o catch em prepareDocumentFile reclassifica como pdf-image (StudentImportModal.tsx:442-445), mas ao tentar a rota visual, renderPdfFirstPageToBase64 chama o mesmo pdfjsLib.getDocument e falha de novo — o erro que chega à professora é o erro técnico bruto do pdfjs (ex.: "PasswordException"), não uma mensagem como "este PDF está protegido por senha".

GSituação real do PDF escaneado e "OCR"

CONFIRMADO POR CÓDIGO — não existe OCR tradicional no sistema (sem Tesseract, sem Google Cloud Vision, sem nenhum motor de reconhecimento de caracteres). O que existe é: o PDF é renderizado em um <canvas> no navegador, convertido para JPEG, e enviado como imagem para o Gemini 2.5 Flash, que faz leitura visual multimodal direta do documento (renderPdfFirstPageToBase64, studentDocumentImportService.ts:426-438).

  • Só a primeira página é renderizada e enviada — pdf.getPage(1) hardcoded (linha 429). Confirmado e disclosed na UI ("Apenas a primeira página será processada" — StudentImportModal.tsx:903), mas continua sendo uma limitação estrutural grave: a maioria dos laudos/anamneses reais tem 2+ páginas.
  • Sem pré-processamento: não há rotação automática, correção de perspectiva, ajuste de contraste, redução de ruído ou detecção de página escura/em branco. A imagem é renderizada em escala 2.0x e comprimida em JPEG qualidade 0.85 — suficiente para a maioria dos casos, mas sem nenhuma correção para fotos tortas ou mal iluminadas.
  • Sem timeout dedicado no cliente — o timeout de 90s está no servidor (index.ts:293, callAIWithRetryAndTimeout(...,0,90_000)); o cliente não tem seu próprio timeout/retry.
  • Sem indicação de confiança por página — só existe um confidence geral por aluno extraído (0 a 1), calculado pelo próprio modelo dentro do JSON de resposta — não há verificação independente de qualidade de imagem antes do envio.
  • Cobrança: os 5 créditos (visual) só são reservados antes da chamada e só são confirmados (cobrados de fato) se pelo menos 1 aluno for salvo — se o OCR/leitura visual falhar ou a confiança média for < 0.25, a função lança erro e a reserva é liberada automaticamente pela Edge Function (studentDocumentImportService.ts:528-532, index.ts:318-339). CONFIRMADO POR CÓDIGO — falha de OCR/leitura visual não cobra crédito no caminho feliz de erro.

HImagens e análise multimodal — achado crítico de MIME type

P0 confirmado por código. Em studentDocumentImportService.ts:440-447, a função fileToBase64 lê o arquivo com FileReader.readAsDataURL e depois descarta o prefixo data:<mimetype>;base64,, mantendo só o payload base64: 

reader.onload  = () => resolve((reader.result as string).split(',')[1]);

Esse valor "puro" (sem prefixo) é enviado como imageBase64 ao Gateway. No servidor, _vertex.ts:46-51 tenta recuperar o tipo MIME original com uma regex sobre o prefixo data:...:

const mimeMatch = imageBase64.match(/^data:([^;]+);base64,/);
const mimeType  = mimeMatch?.[1] || 'image/jpeg';  // ← fallback quando não há prefixo

Como o prefixo já foi removido no cliente, mimeMatch nunca casa, e o Gemini recebe todas as imagens rotuladas como image/jpeg, independentemente do formato real dos bytes. Um .png ou .webp chega à API do Gemini com um inlineData.mimeType que não corresponde aos bytes reais — na melhor hipótese o modelo ainda consegue decodificar (alguns decoders são tolerantes), na pior o modelo falha silenciosamente em interpretar a imagem ou devolve um JSON vazio/genérico.

Prova de que isso é um bug e não uma limitação da plataforma: o mesmo projeto tem outro fluxo de leitura visual, ChecklistUploadModal.tsx:74-81, que faz exatamente a mesma operação mas sem descartar o prefixo:

reader.onload = () => resolve(reader.result as string); // mantém "data:image/png;base64,..."

Isso confirma que a correção é trivial (parar de fazer .split(',')[1] no cliente OU repassar o mimetype real explicitamente) — mas não deve ser feita nesta fase, apenas documentada. CONFIRMADO POR CÓDIGO

Demais pontos de imagem

  • Sim, a imagem é convertida em base64 e enviada inline (não via URL, não via Storage) — a imagem nunca é persistida em nenhum bucket. Bom para privacidade, mas significa que a imagem também não pode ser consultada de novo depois na revisão.
  • Só uma imagem por vez é aceita (sem multiple no input, sem loop de arquivos).
  • Sem alerta de "imagem escura/cortada/desfocada" antes do envio — só um aviso textual genérico pedindo "imagem nítida e bem iluminada".

LEstrutura atual do prompt de extração (sem alterar)

Há dois prompts distintos, ambos em studentDocumentImportService.ts: um para texto (linhas 140-178) e um para imagem (linhas 461-480). Ambos compartilham a mesma filosofia de "não inventar".

Pontos fortes (confirmados por código)

  • Regra explícita e repetida: "NUNCA invente, suponha ou infira informações" — se o dado não está no texto/imagem, omita o campo.
  • Proíbe placeholders como "Não informado"/"N/A" — força omissão real do campo em vez de poluir com string vazia.
  • CID: só extrai se aparecer literalmente um código no padrão (ex.: F84.0) — não deduz a partir de descrição de comportamento.
  • Suporta múltiplos alunos no mesmo documento (array students).
  • needsReview por campo de baixa confiança + confidence geral por aluno.
  • No modo visual, instrui explicitamente confiança baixa (≤0.4) para documentos pouco legíveis.

Pontos fracos identificados

  • Sem exigência de evidência/trecho de origem por campo — o prompt nunca pede ao modelo para citar de onde tirou cada dado, o que impossibilita a revisão "por página" pedida no escopo (Seção O).
  • Sem distinção explícita entre "diagnóstico confirmado" e "hipótese diagnóstica" — o prompt fala em "diagnósticos literalmente presentes", mas não instrui a preservar qualificadores como "suspeita de" ou "em investigação" como metadado separado.
  • Sem instrução anti-capacitismo/infantilização de linguagem — não há uma diretriz explícita para o tom da extração (o que é menos crítico aqui, já que o prompt extrai dados, não gera texto longo, mas os campos livres como observations/recommendations reproduzem o texto de origem sem qualquer filtro).
  • Sem instrução para reconhecer documento irrelevante (ex.: um PDF que não é ficha/laudo/anamnese) — a única defesa é a checagem pós-resposta de que existe pelo menos um name não vazio; um documento genérico contendo qualquer nome próprio pode gerar uma extração espúria de "1 aluno" com poucos campos.
  • Não pede confiança por campo, só confiança geral por aluno — impossibilita destacar "este campo específico está duvidoso, mas o resto está ok" além do flag binário em needsReview.
  • O prompt de texto corta a entrada em 8.000 caracteres antes de ser montado — para documentos longos, o modelo nunca vê o final do documento.

MModelo de resposta e validação

Estrutura de retorno (StudentDocumentDraft, studentDocumentImportService.ts:32-59) cobre bem o essencial: identificação, responsável, diagnóstico/CID/suporte/medicação, perfil pedagógico (habilidades, dificuldades, estratégias, comunicação), contexto (histórico escolar, contexto familiar, observações, recomendações), e metadados de extração (needsReview, confidence).

Faltam explicitamente do modelo de resposta (pedidos no escopo, seção 13, e ausentes do código):

  • nome social, código do aluno, etapa de ensino, sexo distinto de "gênero", endereço do responsável;
  • profissional responsável pelo documento, data do documento, instituição emissora (campos "declarados no documento" que ajudariam a rastrear a origem);
  • tipo de documento detectado, páginas analisadas, campos não encontrados (hoje só existe o inverso — campos encontrados);
  • trechos de evidência e confiança por campo (mencionado acima);
  • divergências entre fontes (não aplicável hoje pois só 1 documento é processado por vez).

Validação: é estrutural, não semântica — JSON.parse + checagem de que students é array não vazio + filtro de nomes vazios (studentDocumentImportService.ts:204-210). Não há verificação de que birthDate seja uma data plausível, que cid siga o padrão CID-10, ou que gender seja um dos 3 valores esperados antes de cair no normalizeImportedStudentFromDocument (que aí sim faz o .includes(['M','F','OTHER'])). Não existe biblioteca de schema (Zod/Yup/AJV) usada aqui — CONFIRMADO POR CÓDIGO, embora o Gateway tenha uma função validateAndRepair genérica (_aiUtils.ts) usada para task: 'json'/'document' — não é específica ao schema de aluno.

NCampos extraídos vs. campos descartados no mapeamento real

databaseService.saveStudent tem uma whitelist explícita de colunas reais da tabela students (REAL_COLUMNS, ~45 colunas) e resolve aliases camelCase/legado de forma consistente e testada. O mapeamento é, de modo geral, sólido: abilities→skills, difficulties→student_difficulties, strategies→student_strategies, communication→communication, diagnosis[0]→primary_diagnosis/diagnosis[1:]→secondary_diagnoses, cid→cid_codes (como array).

Lacuna confirmada: o campo recommendations é extraído pela IA, é mostrado e é editável na tela de revisão ("Recomendações", StudentImportModal.tsx:1438), mas é silenciosamente descartado — saveStudentsFromDocx (studentDocumentImportService.ts:346-381) nunca inclui recommendations no objeto passado a saveStudent, e a tabela students nem tem uma coluna equivalente na whitelist. A professora edita um campo que nunca é salvo. CONFIRMADO POR CÓDIGO

Inconsistência secundária (menor): a whitelist REAL_COLUMNS inclui uma coluna medication dedicada, mas saveStudent nunca a popula — o conteúdo de medicação é sempre gravado em medical_notes (texto livre) via textFromMaybeArray(student?.medication ?? ...). Se algum outro lugar do sistema ler a coluna medication especificamente, ela ficará sempre vazia para alunos importados por este fluxo. HIPÓTESE quanto a impacto downstream (não foi mapeado todo consumidor de medication).

Uso posterior (PEI/PAEE/PDI/Estudo de Caso): _contextBuilder.ts:36-38 busca select('*') da tabela students, portanto tecnicamente os campos salvos por este fluxo estão disponíveis na variável ctx.data.student. Porém, _contextFormatter.ts (responsável por transformar esse contexto em texto de prompt) não faz nenhuma referência direta a ctx.data.student nas buscas realizadas — sugerindo que os campos pedagógicos desse aluno podem estar sendo formatados a partir de uma estrutura diferente (perfis, avaliações) e não diretamente da linha bruta de students. PCobrança de créditos

O desenho geral é reserve → provider → validate → commit/release, com deferCommit: true específico para esta feature: a Edge Function reserva os créditos antes de chamar a IA, mas só confirma o débito depois que o frontend salvar pelo menos 1 aluno no banco. CONFIRMADO POR CÓDIGO — este desenho é mais seguro que o padrão do resto do produto.

Confirmado como seguro

  • Falha do provider de IA (erro, JSON inválido) → reserva liberada automaticamente pela Edge Function antes mesmo de responder ao cliente (index.ts:314-339).
  • Extração com confiança muito baixa (<0.25 no modo visual) → erro lançado no frontend → runAIProcessing zera a referência da reserva (ela já foi liberada no passo acima, pois a chamada ao Gateway lançou erro antes de retornar) — nuance: na verdade, no caminho de baixa confiança, a chamada ao Gateway teve sucesso (a Edge Function já fez commit/deferiu a reserva) e é o frontend quem decide rejeitar depois, em mapVisualDocumentToStudentPayload (linha 528-532) — isso significa que a reserva já teria sido retornada com reservationId, e como a função lança throw antes de retornar o reservationId ao chamador (runAIProcessing), pendingReservationRef nunca é setada — a reserva fica pendurada no banco, "reserved", sem ninguém do frontend saber o ID para liberá-la. Isso é um vazamento de crédito reservado, não apenas hipotético — é uma consequência direta da ordem do código. CONFIRMADO POR CÓDIGO
  • Erro ao salvar no banco → reserva liberada explicitamente (handleDocxSave, catch, StudentImportModal.tsx:594-597).
  • 0 alunos salvos com sucesso (todos falharam) → reserva liberada (linha 585-586).
  • Fechar o modal pelo X ou trocar de modo → libera a reserva (handleClose, switchMode).
  • Desmontagem do componente (React) → libera a reserva no useEffect de cleanup.

Risco confirmado — sem rede de segurança para reservas abandonadas

A RPC reserve_credits (migration 20260520000002_atomic_credit_transactions.sql) debita o saldo (balance) imediatamente ao reservar, não apenas "trava" um valor separado. O deferCommit grava um expires_at de 30 minutos (index.ts:229-231), e existe até um índice dedicado (idx_credit_reservations_expires_at ... WHERE status='reserved') sugerindo que uma rotina de expiração foi planejada — mas essa rotina não existe. Nenhuma pg_cron, função expire_reservations/release_expired, nem Edge Function agendada foi encontrada em todo o diretório supabase/. CONFIRMADO POR CÓDIGO (ausência)

Consequência: se a professora fechar a aba do navegador (crash, F5 forçado, perda de conexão) depois que a IA processou o documento mas antes de confirmar/cancelar pela UI, o useEffect de cleanup do React não roda de forma confiável (fechamento abrupto de aba não garante execução de cleanup assíncrono), e o crédito debitado nunca retorna ao saldo — nem em 30 minutos, nem nunca, pois não há sweep.

Demais pontos confirmados

  • Preço da interface bate com o preço real: CREDITS_DOC_TEXT = 3, CREDITS_VISUAL = 5, ambos vindos de src/config/aiCosts.ts — fonte única, sem divergência.
  • Cobrança é por confirmação (salvar), não por upload — correto e conservador.
  • PDF convertido em imagem para tentar "burlar" classificação (ex.: renomear .jpg como .pdf) não é possível reduzir custo: a detecção é por conteúdo real (tenta extrair texto do PDF; se falhar, cobra 5 créditos), não por extensão.

QPrivacidade e armazenamento

  • Arquivo original: processado 100% no navegador (extração de texto/render de imagem) — nunca é enviado a nenhum bucket de Storage. Só o texto extraído ou a imagem em base64 trafega até a Edge Function, e só até o provider de IA. CONFIRMADO POR CÓDIGO — bom para privacidade (não há bucket público/assinado para auditar aqui, porque não existe).
  • Logs client-side: console.info/console.debug registram apenas metadados (tempo em ms, contagem de caracteres, contagem de alunos, quantidade de campos com baixa confiança) — nunca o conteúdo em si (nome, CID, diagnóstico). CONFIRMADO POR CÓDIGO, boa prática já seguida no projeto.
  • Auditoria server-side (ai_outputs): a Edge Function grava até 500 caracteres do JSON de resultado (que pode conter nome, data de nascimento, CID, diagnóstico, telefone do responsável) na tabela ai_outputs via completeAuditRecord (index.ts:411-419, _audit.ts:93-99). CONFIRMADO POR CÓDIGO — dado sensível de aluno é persistido em uma tabela de auditoria.
  • RLS de ai_outputs: em schema_additions.sql, a tabela ai_requests tem ENABLE ROW LEVEL SECURITY + política por tenant (linhas 525-528), mas ai_outputs não tem nenhuma linha equivalente em todo o arquivo. CONFIRMADO POR CÓDIGO (ausência no schema lido). Se a tabela realmente estiver sem RLS em produção e com grants de leitura para o role authenticated/anon via PostgREST, isso seria uma exposição cross-tenant de dados clínicos — mas a exploração real depende de GRANTs de produção que esta auditoria não tem acesso para verificar. Recomenda-se checar isso com prioridade, mesmo sem tocar em nada agora.
  • Isolamento entre tenants no cadastro do aluno: saveStudent sempre usa o tenant do usuário autenticado, nunca o tenant do payload recebido (databaseService.ts:568-570) — proteção deliberada contra um aluno de outra escola sobrescrever dados por engano.
  • localStorage: nenhuma referência a armazenar o arquivo ou o texto extraído em localStorage/sessionStorage foi encontrada nesta feature.

TArquitetura recomendada — aproveitando o que já existe

Nenhuma peça estrutural nova é necessária. O Gateway já suporta texto estruturado, imagens, resposta JSON e fallback entre providers. Não é necessário trocar de provider, criar tabela nova, nem introduzir um serviço de OCR externo.

A arquitetura-alvo do pedido (classificador → extrator → normalização → IA → validação → revisão → confirmação → persistência → cobrança) já existe hoje nesta ordem — o que falta são reforços pontuais dentro de cada etapa, não uma reestruturação:

  1. Extração de conteúdo: já separada (pdfjs / mammoth / canvas) — precisa de mais páginas e menos truncamento.
  2. Interpretação pedagógica: já no prompt — precisa de evidência por campo.
  3. Validação da resposta: hoje é estrutural — poderia ganhar validação semântica leve (datas, CID) sem exigir biblioteca nova.
  4. Mapeamento: já sólido — precisa só fechar a lacuna do recommendations.
  5. Revisão humana: já real — precisa de indicação "documento não revisitável" mais clara e cancelamento durante processamento.
  6. Confirmação/cobrança: já segura no caminho feliz — precisa fechar o vazamento de reserva de baixa confiança e considerar um job de expiração (fora do escopo imediato, é mudança de banco).
