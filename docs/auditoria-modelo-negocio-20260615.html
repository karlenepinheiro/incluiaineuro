⚡ Resumo Executivo

A auditoria identificou 3 riscos críticos, 3 riscos altos e 4 riscos médios. O risco mais grave é que assinaturas anuais têm current_period_end = now() + 30 dias — idêntico ao mensal — sem nenhum mecanismo interno que renove créditos mensalmente durante os 12 meses. Todo o modelo anual depende exclusivamente de eventos da Kiwify, sem fallback, sem cron e sem validação de período no acesso. Nenhum dado foi alterado durante esta auditoria.

Como o banco diferencia mensal / anual — billing_cycle

A coluna subscriptions.billing_cycle armazena 'monthly' | 'annual' | null. É preenchida por:

OrigemLógica de detecçãoFallback
kiwify-webhook Regex no product_name: /anual|annual/i 'monthly'
activate_purchase_for_user() product_key LIKE '%ANNUAL%' 'monthly'
reconcile_pending_activations() product_key LIKE '%ANNUAL%' 'monthly'
⚠ Assinaturas sem billing_cycle
Contas criadas antes da coluna billing_cycle existir têm NULL. O código aplica fallback para null (não assume mensal nem anual), e a UI exibe o plano sem indicar o ciclo. Não há como saber retroativamente se eram mensais ou anuais.
10

Assinaturas vencidas ainda ativas

🔴 Risco confirmado — acesso indevido
A função checkSubscriptionAccess() verifica apenas o campo status, nunca current_period_end. Se a Kiwify falhar em enviar subscription_overdue, a assinatura fica com status = 'ACTIVE' mesmo após o período expirar. Não existe nenhum job, cron ou pg_cron que faça downgrade automático.

Se o webhook falhar em qualquer etapa → status permanece ACTIVE → acesso continua indefinidamente.

Como créditos mensais são concedidos

Caminho Disparado por Operação na wallet Tipo no ledger Idempotente?
Kiwify webhook order_approved Kiwify → Edge Function RESET balance = créditos do plano monthly_grant Parcial (kiwify_webhook_logs)
Kiwify webhook subscription_renewed Kiwify → Edge Function RESET balance = créditos do plano monthly_grant Parcial

CEO grant manual Painel CEO INCREMENT balance manual_grant Sim (operation_id)
⚠ Webhook bypassa atomic RPCs
Os caminhos 1 e 2 usam setCredits() — operação direta na credits_wallet, fora do sistema atômico (atomic_grant_credits). Isso bypassa a tabela credit_operations e sua idempotência garantida, criando risco de duplicação em eventos repetidos.
13

Mensal e anual renovam crédito da mesma forma?

🔴 Risco crítico — renovação mensal anual não garantida
No código, ambos usam a mesma chamada setCredits(). A diferença está em quem dispara e quando:
  • Mensal: Kiwify envia subscription_renewed a cada 30 dias → créditos renovam automaticamente.
  • Anual: Depende de a Kiwify enviar subscription_renewed mensalmente para planos anuais. Não há documentação no código confirmando isso. Se não enviar, os créditos param após o primeiro mês.

Não existe nenhum pg_cron, Edge Function agendada ou lógica interna que renove créditos mensalmente de forma independente da Kiwify.

15

Onde está implementada a regra "fidelidade 12 meses" (anual)

🔴 Não implementada — risco crítico
Nenhuma lógica no sistema:
  • Define current_period_end = now() + 365 dias para anuais.
  • Impede cancelamento nos primeiros 12 meses.
  • Diferencia o período vigente entre mensal e anual.

Tanto o kiwify-webhook quanto a activate_purchase_for_user() sempre gravam: 

current_period_end = now() + INTERVAL '30 days'   -- independente do billing_cycle!

O campo billing_cycle = 'annual' é gravado corretamente, mas nunca é usado para calcular o período.

Riscos identificados

🔴
Crítico
Assinatura anual expira em 30 dias no banco. current_period_end = now() + 30 days independente do ciclo. Assinante anual aparece como "expirado" após 30 dias.
🔴
Crítico
Nenhum mecanismo interno renova créditos mensalmente para anuais. Sem pg_cron, sem Edge Function agendada. Se a Kiwify não enviar subscription_renewed todo mês, créditos param após o primeiro grant.
🔴
Crítico
checkSubscriptionAccess() ignora current_period_end. Assinante com status = ACTIVE e período vencido mantém acesso irrestrito se webhook falhar.
🟠
Alto
last_reset_at e next_credit_grant_at nunca atualizados. Dashboard exibe "Próxima renovação: —" para todos os usuários, corroendo confiança na plataforma.
🟠
Alto
kiwify-webhook bypassa atomic RPCs. Eventos duplicados podem conceder créditos duas vezes sem a proteção de credit_operations.
🟠
Alto
schema_v16 pode não ter sido executado em produção. Se não foi, PRO tem 50 créditos (não 500) e MASTER tem 70 créditos (não 700) — 10× menos do prometido.

Correções recomendadas por prioridade

  • P1
    Corrigir current_period_end para assinaturas anuais No kiwify-webhook e em activate_purchase_for_user(), quando billing_cycle = 'annual', setar current_period_end = now() + INTERVAL '365 days'. Migração simples de 2 linhas.
  • P1
    Criar mecanismo de renovação mensal de créditos para anuais Edge Function com pg_cron (mensal) que consulta assinaturas com billing_cycle = 'annual' e status = 'ACTIVE' e chama atomic_grant_credits para cada uma — independente de eventos da Kiwify.
  • P1
    Validar current_period_end em checkSubscriptionAccess() Se status = 'ACTIVE' mas current_period_end < now(), retornar OVERDUE automaticamente. Impede acesso indevido quando webhook falhar.
  • P2
    Migrar setCredits() do webhook para atomic_grant_credits Garantir idempotência real no fluxo de ativação via webhook usando o sistema atômico já existente com credit_operations.
  • P2
    Atualizar last_reset_at e next_credit_grant_at ao conceder créditos Incluir essas colunas no UPDATE da credits_wallet em cada grant mensal. Permite que o dashboard mostre datas corretas de renovação.
  • P2
    Confirmar execução de schema_v16_fix_plan_credits.sql em produção Verificar via SQL Editor: SELECT name, ai_credits_per_month, max_students FROM plans;. Se PRO = 50 ou MASTER = 70, executar o script imediatamente.
  • P3
    Mover preços anuais para o banco Adicionar coluna price_brl_annual em plans ou usar kiwify_products.price_brl por produto como fonte única. Permite que CEO altere preços sem deploy.
  • P3
    Backfill de billing_cycle em assinaturas antigas Cruzar kiwify_purchases.product_key com subscriptions.tenant_id para inferir o ciclo de contas sem billing_cycle.
  • P3
    Eliminar ou sincronizar credits_avail com balance Dois campos para o mesmo saldo criam confusão. Remover credits_avail ou garantir que todos os RPCs atualizem ambos consistentemente.
